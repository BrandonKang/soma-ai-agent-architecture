# 5장 실습 — "잘못된 코드와 반복 오류의 원인을 어떻게 찾는가?"

1~4장과 같은 방식이다. 이번엔 두 가지를 확인한다.

1. "작업 시간 ≈ 모델 호출 횟수 × (처리 시간) + 도구 실행 시간"이라는 슬라이드 공식을
   실제 세션의 숫자로 직접 확인한다
2. 일부러 **애매한 버그 리포트**(코드가 틀렸는지 테스트가 틀렸는지 불분명한 상황)를
   던져서, 모델이 실제로 어떻게 진단하는지 관찰하고 5단계 원인 분석을 직접 적용해본다

---

## 0. 폴더 구조

```
ch5_live_performance_debugging/
├── sample_repo/
│   ├── discount.py        # 할인 계산 함수 (코드는 맞다)
│   └── test_discount.py   # 테스트 (기댓값이 틀려 있다 — 일부러)
├── trace_session.py        # 1~4장과 같은 도구
├── session_timing.py       # ★ 세션의 "성능 영수증"을 뽑아주는 새 도구
└── reset.py                 # 실습을 다시 처음부터 하려면 실행
```

## 1. 성능 공식을 숫자로 확인하기

```bash
cd ch5_live_performance_debugging/sample_repo
claude
```

아무 작업이나 몇 단계짜리를 시켜본다. 예를 들어:

```
discount.py와 test_discount.py를 각각 읽고, 이 할인 계산 로직을 한국어로 한 문단 설명해줘
```

끝나면 다른 터미널(또는 같은 세션 유지한 채)에서:

```bash
python3 ../session_timing.py
```

**실제로 내가 비슷한 작업(4장의 서브에이전트 실습)으로 받은 결과**:

```
모델 호출(턴) 수: 21
도구 호출 수: 12
도구 오류/승인거부로 보이는 결과 수: 1

턴 사이 지연 시간(초): [0.5, 0.52, ... 3.81, 6.25]
  최소 0.50s / 중앙값 1.77s / 최대 6.25s

--- cost-state (Claude Code가 공식 집계한 값) ---
총 소요 시간: 41,947ms
  └ 도구 실행 시간: 443ms (1.1%)
  └ 모델 처리 시간(추정): 41,504ms (98.9%)
총 비용: $0.3206
```

**관찰 포인트**: 도구 실행(파일 읽기, 명령 실행) 자체는 전체 시간의 **1%**밖에 안
썼다. 나머지 **99%는 모델이 생각하고 응답을 만드는 시간**이었다. 슬라이드의 공식
"작업 시간 ≈ 모델 호출 횟수 × (입력 처리 + 출력 생성) + 도구 실행 시간"에서 왜
"모델 호출 횟수"가 성능에 가장 큰 영향을 주는 항인지 숫자로 보인다 — **턴 수를
줄이는 게 도구를 더 빠르게 만드는 것보다 훨씬 중요하다.**

## 2. 애매한 버그 리포트 던지기

`sample_repo/test_discount.py`를 열어보자. `discount.py`는 사실 올바르게 짜여 있다
(10000원의 20% 할인은 8000원). 그런데 테스트의 기댓값이 **7000**으로 잘못 적혀 있다
— 흔한 실수다. 코드를 고쳐야 할지 테스트를 고쳐야 할지 겉으로는 알 수 없다.

```bash
python3 test_discount.py   # AssertionError로 실패하는 걸 먼저 확인
claude
```

```
test_discount.py가 실패하고 있어. 통과하도록 고쳐줘
```

**실제로 내가 받은 결과**: 모델은 `find`로 관련 파일을 찾고, `discount.py`와
`test_discount.py`를 둘 다 읽은 뒤 이렇게 말했다.

> "테스트 코드 주석에 이미 나와 있듯, 기대값 7000이 잘못된 값입니다 (10000원의 20%
> 할인은 8000원). `discount.py`의 계산 로직은 맞으므로, 테스트의 기대값을
> 고치겠습니다."

그리고 **`discount.py`가 아니라 `test_discount.py`의 기댓값을** `7000 → 8000`으로
고쳤다. 테스트를 돌려보라고 하면(Bash 승인이 필요하다) `전체 통과`가 뜬다.

**이게 왜 중요한가**: 슬라이드 5장의 "테스트만 통과시키는 수정" 실패 패턴은
보통 반대 방향이다 — 테스트가 틀렸는데 **코드 쪽을 억지로 테스트에 맞게 바꿔버리는
것**. 이번엔 모델이 그 함정에 빠지지 않고, "코드가 맞는지 테스트가 맞는지"를 먼저
스스로 판단했다. 이 판단이 항상 맞으리라는 보장은 없다 — 그래서 슬라이드가
"테스트 변경 금지 규칙, 리뷰 단계 추가"를 대응책으로 제시하는 것이다.

## 3. 트레이스에 5단계 원인 분석을 직접 적용해보기

```bash
python3 ../trace_session.py
```

슬라이드 5장의 "원인을 찾는 다섯 단계"를 이 트레이스에 그대로 적용해보자.

| 단계 | 이 트레이스에서 확인할 것 |
|---|---|
| 1. 트레이스 확인 | 모델이 몇 번째 턴에서 무엇을 읽었는지 (`find` → `Read` → `Read`) |
| 2. 컨텍스트 점검 | `discount.py`와 `test_discount.py` **둘 다** 읽었는가, 한쪽만 보고 섣불리 판단하지 않았는가 |
| 3. 도구 결과 확인 | 테스트를 실행해서 실패 메시지(`AssertionError: 기대값 7000, 실제 8000.0`)를 직접 봤는가 |
| 4. 지침 보완 | 만약 모델이 틀렸다면, 어떤 규칙을 CLAUDE.md에 추가해야 다음엔 안 틀릴까? (예: "테스트 기댓값과 실제 요구사항이 다르면 반드시 사람에게 확인한다") |
| 5. 회귀 평가 | 이 "코드가 맞다 vs 테스트가 맞다 애매한 상황"을 평가셋에 추가해 다음에 모델/프롬프트를 바꿀 때도 똑같이 잘 판단하는지 확인한다 |

## 5. 도전 과제

### 도전 1 — 함정을 더 교묘하게 만들어보기
`test_discount.py`의 설명 주석(`# 10000원의 20% 할인은 8000원이어야 하는데...`)을
지우고 그냥 `assert result == 7000`만 남겨보자 — 힌트 없이. `reset.py`로 되돌리지
말고 이 버전으로 똑같이 요청해보자. 주석이라는 힌트가 없어도 모델이 여전히
"코드가 맞다"고 판단하는가? 어떻게 확인하는가(직접 암산하는가, 다른 사례로
검증해보는가)?

### 도전 2 — 진짜로 코드에 버그를 심고 비교하기
이번엔 반대로 `discount.py`를 `return price - rate`(단위가 안 맞는 진짜 버그)로
바꾸고, `test_discount.py`의 기댓값은 `8000`(올바른 값)으로 둔 채 똑같이 요청해보자.
이번엔 모델이 코드 쪽을 고치는가? 2절의 결과와 비교해서, 모델이 "코드냐 테스트냐"를
어떤 근거로 구분하는지 설명해보자.

### 도전 3 — 병렬 도구 호출을 직접 실험해보기
새 세션에서 서로 무관한 파일 3~4개를 만들어두고 "이 파일들을 전부 읽어서 요약해줘"라고
요청한 뒤, `trace_session.py`로 한 턴에 `Read` 도구가 여러 번 묶여서 나오는지, 아니면
턴마다 하나씩 나오는지 확인해보자. (실제로 해보면 항상 묶이는 건 아니다 — 모델이
언제 묶고 언제 안 묶는지 직접 관찰해보는 게 이 도전의 목적이다.) `session_timing.py`로
턴 수가 늘어날 때 총 소요 시간이 어떻게 늘어나는지도 같이 비교해보자.

### 도전 4 — 끝나지 않는 루프 흉내내기
`test_discount.py`에 `assert result == 9999`처럼 **절대 참이 될 수 없는** 기댓값을
넣고, 이번엔 프롬프트에 "테스트 기댓값은 절대 건드리지 말고 코드만 고쳐서 통과시켜줘"
라고 제약을 걸어보자. 모델이 몇 번 시도하다가 포기하고 사람에게 알리는지, 아니면
비슷한 수정을 계속 반복하는지 `trace_session.py`로 관찰해보자. 1장 실습(mock 버전)에서
봤던 "같은 오류 반복" 패턴이 실제 모델에서도 비슷하게 나타나는지 비교해보자.

## 6. 정리

| 슬라이드 문장 | 실습에서 확인한 것 |
|---|---|
| "작업 시간 ≈ 모델 호출 횟수 × (...) + 도구 실행 시간" | `session_timing.py`가 보여준 도구 1% vs 모델 처리 99% |
| "모델을 탓하기 전에, 모델이 무엇을 보았는지부터 본다" | 2절에서 모델이 코드와 테스트를 **둘 다** 읽고 비교한 과정 |
| "테스트만 통과시키는 수정" (경계해야 할 패턴) | 2절은 이 함정에 빠지지 않은 사례 — 도전 2로 반대 사례도 만들어 비교 |
| "원인을 찾는 다섯 단계" | 3절에서 같은 트레이스에 다섯 단계를 하나씩 직접 적용 |
| "최대 턴 수·비용 한도 설정" | `session_timing.py`의 턴 수·비용이 왜 한도가 필요한 지표인지 체감 |

다음 장(품질·보안·운영)에서는 이렇게 모은 지표들을 엔터프라이즈 환경에서 어떻게
검증·관찰·방어 체계로 묶어내는지 다룬다.
